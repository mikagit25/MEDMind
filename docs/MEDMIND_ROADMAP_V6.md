> Глобальные правила V3–V5 в силе: pytest 0 failed, PROJECT_STATE.md, верификационный
> конвейер для контента, guardrails не ослабляются, i18n en/ru минимум.

## Фаза 1 — E2E smoke-тесты и мониторинг фронтенда (СТРАХОВОЧНАЯ СЕТКА)

**Цель:** ни один релиз не может молча сломать критический путь пользователя.

### Задачи

- **1.1 Playwright** в `frontend/e2e/`: установка, конфиг (chromium достаточно), запуск против локального docker-compose стека (test-БД с сидом; создать `scripts/e2e_seed.py` — тестовый пользователь, тестовый модуль, тестовый NCLEX-набор, тестовый промокод).
- **1.2 Smoke-сценарии (10 штук, каждый ≤30 сек):**
  1. Регистрация → онбординг с диагностическим квизом → попадание на стартовый план;
  2. Логин → открыть модуль → пройти урок → урок отмечен завершённым;
  3. NCLEX демо (без оплаты): старт → ответ на mcq и sata → результат показан;
  4. Dose-calc тренажёр: задача → ввод ответа → пошаговое решение отображено;
  5. Флешкарты: сессия повторения → оценка карточки → счётчик уменьшился;
  6. AI-тьютор: вопрос в patient-режиме → ответ содержит дисклеймер;
  7. Оплата с промокодом (тестовый режим платёжки): применение кода → цена изменилась → checkout открывается;
  8. Публичный контур без auth: страница темы → глоссарий → публичный квиз проходится;
  9. Поиск (Cmd+K): запрос → результаты → переход на результат;
  10. Смена языка en→ru: интерфейс переключился, ключевые страницы не падают.
- **1.3 CI-интеграция:** отдельный job `e2e` в GitHub Actions на каждый PR и push в main; при падении — деплой блокируется (если деплой автоматический) или красный статус (если ручной). Артефакты: скриншоты и трейсы упавших тестов.
- **1.4 Sentry на фронтенде** (web + mobile через @sentry/nextjs и sentry-expo): DSN в env, sourcemaps в билде, фильтрация шума (расширения браузера, отменённые запросы); те же аларм-каналы, что у backend-Sentry.
- **1.5 Uptime-проверка:** лёгкий healthcheck-скрипт или внешний монитор (если уже есть — задокументировать в docs/OPS.md; если нет — cron-скрипт на сервере: каждые 5 минут проверка /health фронта и бэка, алерт в Telegram через существующую интеграцию).

### Приёмка
- Все 10 сценариев зелёные локально и в CI; намеренная поломка (закомментировать кнопку логина) валит E2E-job.
- Тестовая JS-ошибка на фронте появляется в Sentry.

## Фаза 2 — NCLEX: rationales для каждого варианта

**Цель:** качество объяснений уровня UWorld — главный фактор, за который платят в exam-prep.

### Задачи

- **2.1 Схема вопроса**: добавить `rationales: JSON` — объяснение для КАЖДОГО варианта: `{option_id: {text, why: 'correct'|'incorrect'}}` + `key_takeaway: str` (одно предложение — главный вывод) + `test_taking_tip: str | None` (стратегия: «когда видите 'первым действием' — ищите оценку состояния, не вмешательство»).
- **2.2 Генератор**: обновить промпт генерации NCLEX-вопросов — rationales обязательны для всех вариантов, с сестринской логикой (приоритизация по ABC, Maslow, nursing process); прогнать дозаполнение существующего банка скриптом (идемпотентно, батчами, `--max N`).
- **2.3 Верификация**: rationales проходят существующий claim-checking конвейер как часть вопроса (утверждения в объяснениях — тоже медицинские факты).
- **2.4 UI:** после ответа — объяснение выбранного варианта раскрыто, остальные сворачиваемы; key takeaway выделен; в режиме экзамена rationales показываются только в review после завершения (как в реальном NCLEX-препе).
- **2.5 «Отметить вопрос»**: флаг вопроса пользователем (непонятен/ошибка) → очередь в админке контента.

### Приёмка
- 100% вопросов NCLEX-банка имеют rationales для всех вариантов (скрипт-проверка);
- E2E-сценарий №3 расширен проверкой отображения rationale.

## Фаза 3 — NCLEX Readiness Score

**Цель:** одна цифра, ради которой студент возвращается каждый день.

### Задачи

- **3.1 Модель оценки** `backend/app/services/readiness.py`:
  - точность по каждой категории Client Needs (8 категорий NCLEX), взвешенная по официальному распределению экзамена;
  - вес свежести: последние 7 дней × 1.5, последние 30 × 1.0, старше × 0.5;
  - поправка на сложность отвеченных вопросов (лёгкие верные дают меньше, чем сложные);
  - минимальный порог данных: score не показывается до 50 отвеченных вопросов («ответьте ещё N вопросов для оценки»);
  - результат: 0–100 + уровень (Below passing / Borderline / Passing range / High) + топ-3 слабые категории.
  - **Формулировка в UI — юридически аккуратная**: «Readiness estimate based on your practice performance», НЕ «вероятность сдачи экзамена» (мы не можем гарантировать корреляцию с реальным NCLEX; дисклеймер в тултипе).
- **3.2 Дашборд NCLEX-хаба**: большой score с трендом за 30 дней (график), разбивка по категориям (радар или бары), кнопка «Тренировать слабую категорию» → сессия вопросов из неё.
- **3.3 Пересчёт**: инкрементально после каждой сессии (не realtime на каждый ответ); кэш.
- **3.4 Событие** `readiness_updated` в аналитику — для lifecycle-писем Фазы 5.

### Приёмка
- Score появляется после 50 ответов, меняется после сессии, слабые категории соответствуют реальной статистике тестового пользователя (юнит-тесты на модель с фикстурами: заведомо слабая категория попадает в топ-3).

## Фаза 4 — Учебный план от даты экзамена

**Цель:** дедлайн как retention-механизм.

### Задачи

- **4.1 Модель** `ExamPlan`: `user_id, exam_type (nclex_rn|nclex_pn|...), exam_date, daily_minutes (15/30/60), created_at, status`.
- **4.2 Генератор плана** `backend/app/services/study_planner.py`: от сегодня до exam_date распределяет: ежедневные сессии вопросов (объём от daily_minutes), фокус-темы по слабым категориям (из readiness), 2–3 полных mock-экзамена (за 3 недели, 2 недели и 4 дня до даты), день отдыха перед экзаменом. План — детерминированные правила, НЕ AI (предсказуемость и тестируемость).
- **4.3 UI:** визард «Когда экзамен?» в NCLEX-хабе → календарь плана (сегодняшняя задача крупно, неделя списком); выполнение задач дня двигает прогресс; перенос даты пересобирает план.
- **4.4 Напоминания:** утреннее push/email «задача на сегодня» (существующий scheduler), особые письма за 7 и 1 день до экзамена; после даты — письмо «как прошло?» с опросом сдал/не сдал (данные для будущей валидации readiness score!).
- **4.5 Аналитика:** события plan_created, plan_task_completed, plan_rescheduled.

### Приёмка
- План на 30 дней генерируется корректно (юнит-тест: mock-экзамены в правильных точках, день отдыха на месте); смена даты пересобирает; напоминание уходит (тест с мок-временем).

## Фаза 5 — Lifecycle-коммуникации

**Цель:** сценарные цепочки писем/push вместо только событийных.

### Задачи

- **5.1 Инфраструктура кампаний** `backend/app/services/lifecycle.py` + таблица `lifecycle_sends (user_id, campaign, step, sent_at)` — идемпотентность: шаг кампании не отправляется дважды. Ежедневный cron-джоб оценивает условия всех кампаний.
- **5.2 Кампании (первый набор):**
  - **Онбординг** (роль-зависимый контент): день 1 «начните с этого» (стартовый план), день 3 «попробуйте AI-тьютора / dose-calc» (что не тронуто), день 7 «ваша первая неделя» (статистика);
  - **Реактивация**: 7 дней неактивности → «вы остановились на 40% модуля X, осталось Y уроков»; 21 день → дайджест нового контента; 45 дней → последнее письмо, дальше тишина (не спамить);
  - **Стрик под угрозой**: вечером, если сегодня нет активности и стрик ≥3 (уже есть push — добавить email-вариант по настройке);
  - **Readiness-прогресс**: раз в неделю активным NCLEX-пользователям «ваша готовность: 72% (+4)»;
  - **Exam countdown**: из Фазы 4.
- **5.3 Настройки пользователя**: страница управления подписками (каждая кампания отключаема отдельно), обязательная unsubscribe-ссылка в каждом письме, немедленное применение отписки (тест).
- **5.4 Шаблоны**: единый базовый шаблон, i18n (язык пользователя), тёмная/светлая совместимость, plain-text версия.
- **5.5 Метрики**: события email_sent/email_opened (пиксель)/email_clicked (utm) в аналитику; в админ-дашборде — таблица кампаний с open/click rate.

### Приёмка
- Тест идемпотентности: двойной запуск cron не дублирует письмо; отписка от кампании останавливает её шаги; тестовый прогон онбординг-цепочки на тестовом пользователе с мок-временем проходит все шаги.

## Фаза 6 — Укрепление денежных механик

**Цель:** промокоды, партнёрка и биллинг выдерживают злоупотребления и сбои.

### Задачи

- **6.1 Промокоды — граничные случаи** (тесты на каждый): истёкший код в момент checkout; повторное применение тем же пользователем; код с лимитом использований — гонка на последнем использовании (блокировка на уровне БД); стекание кода с активным триалом.
- **6.2 Webhook платёжки**: идемпотентная обработка (повторный webhook не дублирует подписку), очередь ретраев при падении обработчика, алерт в Telegram при webhook-ошибке; сверочный cron: статусы подписок в БД vs платёжка, расхождения — в отчёт.
- **6.3 Dunning**: неудачное продление → 3 письма (сразу / +3 дня / +7 дней) с линком обновить карту → grace-период 7 дней → даунгрейд на free (не удаление данных).
- **6.4 Партнёрка — анти-фрод**: запрет самореферала (совпадение user_id, email-домена+похожести, платёжного метода); флаг подозрительности: ≥3 регистрации с одного IP/устройства по одной ссылке → комиссия в статус hold до ручной проверки; выплата комиссии только после того, как реферал оплатил и прошёл период возврата (14 дней), не в момент регистрации; админ-раздел: подозрительные начисления с кнопками approve/reject.
- **6.5 Аудит-лог денег**: таблица `billing_events` — каждое изменение подписки/комиссии/промо с причиной и источником (webhook/admin/system); просмотр в админке.

### Приёмка
- Все граничные тесты 6.1 зелёные; повторный webhook не создаёт дубль (тест); самореферал блокируется (тест); dunning-цепочка проходит на мок-времени.
