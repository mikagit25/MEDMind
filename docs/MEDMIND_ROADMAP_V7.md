# MedMind AI — Roadmap V7: «Калибровка банка и обратная петля»

> Положить в репозиторий: `docs/MEDMIND_ROADMAP_V7.md`. Команды — в конце.
> Глобальные правила V3–V6 в силе: pytest 0 failed, E2E зелёные, PROJECT_STATE.md,
> верификационный конвейер для контента, guardrails не ослабляются, i18n en/ru минимум,
> параметры экзаменов только из ExamDefinition, recall-вопросы запрещены.
>
> **Проблема, которую решает V7:** поле `MCQQuestion.difficulty` — строка от AI-генератора,
> а не измеренная величина. Из-за этого CAT-симуляция, Readiness Score и подбор вопросов
> работают на непроверенных данных, а битые вопросы (неверный ключ, двусмысленность,
> мёртвые дистракторы) не выявляются. V7 превращает поведение пользователей
> в калибровочный инструмент банка.

## Фаза 1 — Психометрика вопросов (ФУНДАМЕНТ V7)

### Задачи

- **1.1 Модель статистики.** Таблица `question_stats` (миграция), одна строка на вопрос (+опционально на срез `exam_slug`, если вопрос в нескольких экзаменах):
  - `question_id`, `exam_slug (nullable)`;
  - `attempts` (число зачтённых попыток), `correct_count`;
  - `p_value: float` — доля верных (= correct_count / attempts);
  - `option_distribution: JSONB` — сколько раз выбран каждый вариант (для sata — частота каждого набора/варианта; для calculation — гистограмма отклонений от верного);
  - `discrimination: float | None` — индекс дискриминации;
  - `avg_time_seconds: float`;
  - `sample_size_ok: bool` (attempts ≥ порога, порог в конфиге, default 40);
  - `computed_difficulty: enum('very_easy','easy','medium','hard','very_hard') | None` — из p_value по границам в конфиге (ориентир: >0.90 very_easy, 0.75–0.90 easy, 0.50–0.75 medium, 0.30–0.50 hard, <0.30 very_hard);
  - `health: enum('ok','review_low_p','review_high_p','review_low_discrimination','review_dead_distractor','review_key_suspect')`;
  - `last_computed_at`.
  - Индексы: `(health)`, `(sample_size_ok, discrimination)`.

- **1.2 Учёт попыток.** Ввести (или переиспользовать существующую) таблицу ответов `question_attempts`: `question_id, user_id, exam_slug, selected (JSONB — что выбрал), is_correct, time_seconds, session_id, session_type ('practice'|'exam'|'mock'|'srs'), created_at`.
  - **Правила зачёта в статистику** (важно для чистоты данных): в психометрику попадает **только ПЕРВАЯ попытка пользователя на вопрос** и только из сессий `exam|mock|practice` (не из `srs`-повторений и не из повторных прохождений). Иначе p_value поедет вверх из-за заучивания.

- **1.3 Расчёт метрик** `backend/app/services/psychometrics.py`, ночной cron (плюс ручной запуск с `--exam`, `--since`, `--dry-run`):
  - `p_value` и `option_distribution` — прямой агрегат;
  - **дискриминация** — метод верхней/нижней групп: по каждой завершённой сессии считаем итоговый балл пользователя в сессии; берём верхние 27% и нижние 27% сессий; `discrimination = p_upper − p_lower`. Альтернатива (предпочтительна, если проще выразить в SQL): точечно-биссериальная корреляция между верностью ответа на вопрос и итоговым баллом сессии. Реализовать одну, вторую — TODO с обоснованием в коде;
  - интерпретация (в конфиг): ≥0.30 хорошо, 0.15–0.30 приемлемо, 0.0–0.15 слабо, **<0 — красный флаг (сильные отвечают хуже слабых → почти всегда ошибка в ключе или двусмысленность)**;
  - **анализ дистракторов**: вариант с 0 выборов при `attempts ≥ порога` → `review_dead_distractor`; неверный вариант, выбираемый чаще верного → `review_key_suspect`;
  - `health` выставляется по приоритету: key_suspect > low_discrimination (<0) > low_p (<0.20) > high_p (>0.95) > dead_distractor > ok.

- **1.4 Замена статической сложности.** Везде, где используется `difficulty` (подбор вопросов, CAT, readiness, adaptive), читать `computed_difficulty` при `sample_size_ok=true`, иначе — фолбэк на статическую `difficulty` от генератора. Единая функция-геттер `get_effective_difficulty(question)` — чтобы фолбэк был в одном месте и покрыт тестом.

- **1.5 Тесты:** p_value/дискриминация на фикстурах с известным ответом (посчитать вручную в тесте); только первая попытка учитывается; sata/ordered/calculation корректно агрегируются; фолбэк сложности; отрицательная дискриминация ставит health=review_low_discrimination.

### Приёмка
- Cron считает метрики по существующим данным (прогнать на проде-копии/стейджинге), в отчёт: сколько вопросов достигли порога выборки, распределение health.
- `get_effective_difficulty` используется во всех точках подбора вопросов (grep-проверка: прямых обращений к `question.difficulty` в логике подбора не осталось).

## Фаза 2 — Дашборд «Здоровье банка» + ревью-очередь

### Задачи

- **2.1 Админ-страница `/admin/question-health`:**
  - сводка: всего вопросов / достигли порога выборки / по health-категориям / средняя дискриминация по экзамену;
  - таблица-очередь: вопросы с `health != 'ok'`, сортировка по attempts (сначала те, что видит много людей — они вредят сильнее всего);
  - карточка вопроса: текст, варианты с распределением выборов (бар на каждый вариант), p_value, дискриминация, avg_time, rationale;
  - действия: `Approve as is` (health→ok, пометка ручной проверки), `Send to regeneration` (флаг для генератора: перегенерировать вопрос по той же теме/категории), `Fix key` (сменить верный ответ — с записью в аудит), `Retire` (вопрос исключается из выдачи, остаётся в БД).
- **2.2 Статус вопроса**: добавить `MCQQuestion.status: enum('active','retired','pending_fix')`; выдача вопросов фильтрует только `active`. Retire не удаляет и не ломает историю попыток.
- **2.3 Связка с жалобами пользователей**: существующий «Отметить вопрос» (V6 Фаза 2.5) поднимает вопрос в ту же очередь с пометкой `user_flagged` и счётчиком жалоб — приоритет сортировки.
- **2.4 Аудит**: любое изменение вопроса (ключ, retire, regeneration) пишется в `content_audit_log` (кто, когда, что было, что стало).
- **2.5 Регенерация**: скрипт `regenerate_flagged_questions.py` — берёт вопросы с флагом regeneration, генерирует замену по той же категории/теме через существующий конвейер (с rationales + verification), новый вопрос помечается `replaces_question_id`, старый → retired.

### Приёмка
- Очередь показывает проблемные вопросы; retire убирает вопрос из выдачи (тест); смена ключа пишется в аудит; регенерация создаёт замену со статусом passed.

## Фаза 3 — Пост-экзаменационная петля

**Цель:** исходы реальных экзаменов валидируют Readiness Score и калибруют веса blueprint.

### Задачи

- **3.1 Модель** `ExamOutcome`: `user_id, exam_slug, exam_date, result: enum('passed','failed','postponed','no_answer'), reported_at, readiness_at_exam: float | None` (снимок score на дату экзамена — фиксировать заранее cron'ом за день до даты!), `self_reported_score: str | None`.
- **3.2 Опрос** (письмо + in-app баннер через 2 дня после `ExamPlan.exam_date`, повтор через 7 дней, максимум 2 напоминания):
  - шаг 1: результат (сдал / не сдал / перенёс);
  - шаг 2 (опционально, по темам — **никаких дословных вопросов, это NDA**): «Какие темы встречались чаще, чем вы ожидали?» — мультиселект категорий blueprint; «К чему наша подготовка подготовила хуже всего?» — мультиселект + свободное поле;
  - шаг 3: NPS-вопрос («насколько вероятно порекомендуете MedMind?») — заодно продуктовая метрика.
  - Явная плашка: «Не присылайте нам вопросы с экзамена — это нарушает правила экзаменационного органа. Нас интересуют только темы.»
- **3.3 Валидационный отчёт** `/admin/readiness-validation`: таблица «диапазон readiness (0–50, 50–60, 60–70, 70–80, 80+) × доля сдавших»; число исходов в каждом диапазоне; предупреждение «недостаточно данных» при n<20 в диапазоне. Плюс экспорт CSV.
- **3.4 Калибровка blueprint**: агрегат «темы, отмеченные как недооценённые» по каждому экзамену → отчёт для ручного решения об изменении весов (НЕ автоматическое изменение весов: официальный blueprint приоритетнее, отчёт лишь подсказывает, где усилить банк и модули).
- **3.5 Осторожность в коммуникации**: пока n исходов < 100 по экзамену, нигде публично не заявлять корреляцию score↔сдача. Внутренний отчёт — да, маркетинг — нет. Прописать это в комментарии к отчёту.

### Приёмка
- Опрос уходит и заполняется (E2E или тест с мок-временем); снимок readiness фиксируется до даты экзамена; отчёт валидации строится; отписка от опроса работает.

## Фаза 4 — Вопрос ↔ AI-тьютор

**Цель:** непонятое объяснение не оставляет студента в тупике.

### Задачи

- **4.1 Кнопка «Объясни иначе»** в экране ответа на вопрос (practice/review; в exam mode — только в разборе после завершения). Передаёт в тьютор контекст: текст вопроса, варианты, выбранный ответ пользователя, верный ответ, rationale, категория, экзамен.
- **4.2 Промпт** `prompts/question_followup.py`: объяснить проще и другим путём (аналогия, мнемоника, разбор «почему привлекателен выбранный дистрактор»); НЕ выдавать другие вопросы банка; язык — язык интерфейса пользователя; для nurse-контекста — сестринская логика приоритизации.
- **4.3 Быстрые follow-up чипы**: «Почему не вариант C?», «Дай мнемонику», «Объясни как для новичка», «Похожая ситуация в практике».
- **4.4 Лимиты**: считается в дневную AI-квоту тарифа; для free — часть демо-лимита; роутинг на Haiku.
- **4.5 Аналитика**: событие `question_followup` (категория, тип чипа) — вопросы с частыми follow-up = кандидаты на переписывание rationale → в очередь Фазы 2 при превышении порога.

### Приёмка
- Полный цикл на web и mobile; в exam mode кнопка недоступна до завершения; события пишутся; вопросы с частыми follow-up появляются в очереди здоровья банка.

## Фаза 5 — Сравнение с сообществом (на данных Фазы 1)

### Задачи

- **5.1 На экране ответа**: «Верно отвечают N% готовящихся» (только при `sample_size_ok`, иначе не показывать) — плюс подсветка, если пользователь попал в меньшинство, ответившее верно («сложный вопрос — вы справились»).
- **5.2 В аналитике пользователя**: перцентиль по категориям в разрезе выбранного экзамена («точность по фармакологии выше, чем у 68% готовящихся к SNLE»). Считать по пользователям с ≥50 ответами, обновлять ночным cron, кэшировать.
- **5.3 Приватность**: только агрегаты, минимальный размер группы для показа перцентиля — 30 пользователей (иначе «недостаточно данных»); никаких имён и никакой возможности сопоставить с конкретным человеком.

### Приёмка
- Проценты показываются только при достаточной выборке (тест на пороги); перцентиль совпадает с прямым расчётом на фикстурах.

## Фаза 6 — Разбор mock-экзамена

### Задачи

- **6.1 Отчёт после mock** (страница сессии, сохраняется в истории):
  - счёт + сравнение с проходным порогом экзамена (из реестра);
  - разбивка по категориям blueprint с дельтой к целевому уровню;
  - **тайминг**: график времени на вопрос, отметка вопросов с аномально долгим ответом, предупреждение «на реальном экзамене вы бы не успели» при превышении лимита;
  - **паттерны ошибок**: правила-детекторы (не AI) на основе типа и категории вопросов, например: доля ошибок в `ordered`-вопросах существенно выше средней → «в вопросах на приоритизацию: проверьте, не выбираете ли вмешательство раньше оценки состояния»; ошибки в `calculation` → «повторите dose-calc тренажёр»; ошибки в вопросах с «first/priority/initial» в тексте → отдельный паттерн. Набор детекторов — в конфиге, минимум 5;
  - «Тренировать слабое» → сессия из провальных категорий;
  - экспорт отчёта в PDF (переиспользовать генератор сертификатов).
- **6.2 История mock'ов**: график динамики счёта по всем mock'ам пользователя рядом с Readiness Score.
- **6.3 Событие** `mock_completed` с разбивкой — в аналитику.

### Приёмка
- Отчёт строится по завершённому mock'у; детекторы срабатывают на подготовленных фикстурах (сессия с намеренно провальными ordered-вопросами даёт соответствующий паттерн); PDF выгружается.

## Порядок и зависимости

```
Фаза 1 → Фаза 2 → Фаза 3 → Фаза 4 → Фаза 5 → Фаза 6
Фаза 1 обязательна первой: Фазы 2, 5 и частично 6 питаются её метриками.
Фазы 3 и 4 независимы друг от друга — можно менять порядок.
Фазу 3 полезно включить как можно раньше: данные накапливаются со временем.
```

## Сквозные требования

1. Ничего из V7 не изменяет содержимое вопросов автоматически — только помечает и предлагает; изменения ключа и retire делает человек через админку с аудитом.
2. Психометрика считается на первых попытках; повторные прохождения и SRS в статистику не идут.
3. Все пороги (размер выборки, границы p_value, интерпретация дискриминации, минимальная группа для перцентиля) — в конфиге, не в коде.
4. PROJECT_STATE.md: раздел «Bank health» с текущим распределением health и числом калиброванных вопросов по экзаменам.
