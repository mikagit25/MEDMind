# MedMind AI — Roadmap V5: «Retention, практика и социальное обучение»

> **Как использовать:**
> 1. Положить в репозиторий: `docs/MEDMIND_ROADMAP_V5.md`, закоммитить.
> 2. В Claude Code вставить стартовую команду (раздел «Команды» в конце).
> 3. Фазы по порядку. Фазы 1–2 — фундамент для измерения эффекта всех остальных.
>
> **Контекст:** V3 (публичный контур) и V4 (верификация, trust, enterprise) выполнены.
> V5 отвечает на три вопроса: почему пользователи уходят (аналитика),
> зачем возвращаться каждый день (point-of-care, SRS статей),
> и как учиться вместе (классы, группы).

---

## Глобальные правила (правила V3/V4 остаются в силе)

1. Перед фазой читать `PROJECT_STATE.md` и этот файл. Коммиты `feat(v5-phase-N)`.
2. `pytest tests/` — 0 failed после каждой фазы. Обновлять PROJECT_STATE.md (шапку и таблицу).
3. Guardrails patient-режима и исключение дозировок из публичного контура не ослабляются. **Исключение Фазы 3:** point-of-care режим показывает дозировки ТОЛЬКО аутентифицированным пользователям с ролью специалиста — как текущий drug database.
4. Все новые пользовательские тексты — через i18n (en/ru минимум, остальные — ключи с fallback).
5. Приватность аналитики (Фаза 1): никаких сторонних трекеров, только собственная БД; IP не хранить в сыром виде; события не содержат медицинского содержимого запросов пользователя (только факт и тип действия).

## Фаза 0 — Синхронизация витрины (быстрая, 1 сессия)

**Цель:** публичные цифры соответствуют реальности и обновляются сами.

- **0.1** Endpoint `GET /public/stats` (кэш 6ч): реальные счётчики из БД — модули (published), статьи (verified), препараты, языки, флешкарты.
- **0.2** Лендинг, `/enterprise`, `/about`: цифры берутся из этого endpoint'а (серверный fetch при SSG/ISR), хардкод удалить.
- **0.3** README: обновить цифры на актуальные + скрипт `scripts/update_readme_stats.py`, который подставляет счётчики в README между маркерами `<!-- stats:start -->` / `<!-- stats:end -->`.

**Приёмка:** grep по frontend не находит хардкоженных «833+», «80+», «124+»; лендинг показывает живые цифры.

## Фаза 1 — Продуктовая аналитика и retention-дашборд (ФУНДАМЕНТ)

**Цель:** видеть D1/D7/D30 retention, воронку онбординга и брошенные модули. Без сторонних сервисов (GDPR).

### Задачи

- **1.1 Событийная модель.** Таблица `analytics_events` (миграция): `id, user_id (nullable для анонимов), anon_id (cookie uuid), event_type, entity_type, entity_id, metadata JSON (без свободного текста!), locale, platform (web/mobile), created_at`. Индексы по `(event_type, created_at)`, `(user_id, created_at)`. Партиционирование по месяцам, если объём позволит — иначе TODO-комментарий.
- **1.2 Трекинг-endpoint** `POST /analytics/track` (rate-limited, batch до 20 событий). Клиентский хелпер `frontend/lib/analytics.ts` с очередью и sendBeacon на выгрузку.
- **1.3 Базовый набор событий** (внедрить вызовы): `signup`, `onboarding_step` (номер шага), `onboarding_completed`, `lesson_started`, `lesson_completed`, `module_started`, `module_completed`, `flashcard_review`, `ai_question` (только режим и специальность, НЕ текст вопроса), `quiz_completed`, `public_page_view` (slug), `search` (только факт, не запрос), `app_open` (mobile).
- **1.4 Retention-дашборд в админке** `/admin/analytics`:
  - когорты по неделе регистрации × D1/D7/D30 retention (таблица-теплокарта);
  - воронка онбординга: signup → onboarding_completed → first lesson_started → first lesson_completed (проценты перехода);
  - «брошенные модули»: топ-10 модулей по доле module_started без module_completed за 30 дней;
  - DAU/WAU/MAU график за 90 дней.
  - Все запросы — SQL-агрегаты с кэшем 1ч, не realtime.
- **1.5 Ретенция данных**: события старше 12 месяцев агрегируются в дневные сводки и удаляются (cron-скрипт + запись в docs).

**Приёмка:** события пишутся с web и mobile; дашборд отображает 4 блока; в metadata нет свободного текста пользователей (тест на schema); pytest зелёный.

## Фаза 2 — Онбординг с диагностикой уровня

**Цель:** первые 5 минут нового пользователя ведут к первому «ага-моменту».

- **2.1 Диагностический квиз** в onboarding-flow (после выбора роли): 6–8 адаптивных вопросов из существующего банка MCQ выбранной специальности (лёгкий → при верном ответе сложнее). Для роли «пациент/любознательный» — пропускается.
- **2.2 Результат** → `user.preferences.level: beginner|intermediate|advanced` + стартовые рекомендации: 3 модуля под уровень и специальность (использовать существующий recommendations-механизм, добавив вес уровня).
- **2.3 Первый экран после онбординга**: не пустой dashboard, а «Ваш стартовый план» — 3 рекомендованных модуля + CTA начать первый урок (одним кликом).
- **2.4 Событийность**: шаги квиза и выбор трекаются (Фаза 1) — воронка онбординга станет измеримой сразу.

**Приёмка:** новый пользователь-студент проходит квиз ≤3 минут и попадает на первый урок в ≤2 клика от конца онбординга; уровень сохранён и влияет на рекомендации (тест).

## Фаза 3 — Point-of-Care режим («Практика»)

**Цель:** сценарий «я на работе, нужен ответ за 10 секунд» — причина открывать MedMind каждый день, а не только перед экзаменом.

### Задачи

- **3.1 Маршрут `/practice`** (web + экран в mobile): единая строка поиска с мгновенными результатами (существующий поиск + приоритет препаратов/калькуляторов/алгоритмов над учебным контентом), крупные плитки: Препараты · Взаимодействия · Калькуляторы · Алгоритмы · Нормы лабораторных показателей.
- **3.2 Клинические алгоритмы**: новый тип контента `algorithm` (миграция + схема): пошаговое дерево «состояние → действия» (JSON-структура шагов с ветвлением, как в case simulator, но справочное). Сгенерировать первые 10 алгоритмов из существующих модулей через AI + верификация конвейером V4 (статусная модель обязательна). Примеры: анафилаксия, гипогликемия, остановка сердца (BLS/ACLS-обзор), отравление у собаки/кошки (vet).
- **3.3 Нормы лабораторных показателей**: справочная таблица (human + vet: собака/кошка) с поиском; данные — новый JSON в `backend/app/data/`, источник указать в записи (гайдлайны).
- **3.4 Скорость как требование**: `/practice` и поиск в нём — серверный рендер + кэш; целевой TTFB < 500ms, поиск отклик < 300ms (замерить и записать в PR).
- **3.5 Доступ**: препараты с дозировками и взаимодействия — только специалистам (существующее правило); алгоритмы и нормы — тоже за auth; публичной версии у /practice нет.
- **3.6 Mobile**: «Практика» — отдельная вкладка нижней навигации; работает офлайн для препаратов и норм (WatermelonDB-синхронизация справочников).

**Приёмка:** сценарий «открыл → нашёл взаимодействие двух препаратов» ≤3 действий; 10 алгоритмов со статусом passed; офлайн-препараты на mobile работают в авиарежиме (ручная проверка, скриншоты в PR).

## Фаза 4 — Социальное обучение: классы и группы

**Цель:** преподаватель приводит 30 студентов одним приглашением; студенты учатся вместе.

### Задачи

- **4.1 Модель классов** (миграции): `Class (id, name, owner_id, invite_code, created_at)`, `ClassMember (class_id, user_id, role: teacher|student, joined_at)`, `Assignment (class_id, module_id|quiz_id, due_at, created_at)`, `AssignmentStatus (assignment_id, user_id, status, score, completed_at)`.
- **4.2 Кабинет преподавателя** (расширить существующий `/teacher`): создать класс → получить invite-ссылку/код → раздать задания (модуль или квиз + дедлайн) → таблица успеваемости (кто прошёл, баллы, просрочки) → экспорт CSV.
- **4.3 Студент**: вступление по коду; блок «Мои задания» на dashboard с дедлайнами; уведомление за 48ч до дедлайна (существующий механизм нотификаций).
- **4.4 Учебные группы (лайт)**: студенты класса видят агрегированный прогресс группы («класс прошёл 64% модуля») и опциональный внутриклассовый лидерборд (opt-in, как глобальный).
- **4.5 Совместные колоды**: владелец колоды может добавить соавторов по email/username; соавторы добавляют карточки; история изменений (кто добавил карту).
- **4.6 Q&A под модулем**: расширить существующие комментарии типом «вопрос» — вопросы поднимаются вверх, автор модуля/преподаватель может пометить ответ «принятым»; AI-подсказка преподавателю: черновик ответа по содержимому урока (кнопка, не автопост).
- **4.7 Enterprise-связка**: классы доступны в enterprise-пространствах — это и есть «team learning» для корпоративных клиентов; отчёт класса попадает в месячный enterprise-отчёт.

**Приёмка:** полный цикл вручную: преподаватель создал класс → студент вступил по коду → получил задание → прошёл → преподаватель видит балл и экспортирует CSV. RBAC-тесты: студент не видит чужой класс, не может создавать задания.

## Фаза 5 — Spaced repetition для статей и уроков

**Цель:** прочитанное не забывается — контент конвертируется в долгосрочное знание.

- **5.1** После `lesson_completed` / прочтения статьи (залогиненным): предложение «Закрепить» → 3 авто-вопроса по содержимому (реиспользовать механизм AI MCQ generation из Phase 10 бэклога, кэшировать вопросы per-lesson).
- **5.2** Согласившимся — материал попадает в SM-2 очередь как «знание» (новый тип reviewable-сущности рядом с флешкартами): повторные мини-проверки через 1 / 3 / 7 / 21 день.
- **5.3** Единая очередь повторений на dashboard: карточки + знания в одном счётчике «К повторению сегодня»; push/email-напоминание использует существующий механизм.
- **5.4** Настройка в профиле: выключить закрепление статей (default: спрашивать после каждой).

**Приёмка:** урок → закрепить → вопрос появился в очереди на следующий день (тест с фиксацией времени); отказ — не появляется.

## Фаза 6 — Сертификаты и экспорт прогресса

**Цель:** прохождение модуля превращается в документ для CPD/работодателя.

- **6.1** PDF-сертификат по завершении модуля (score квиза ≥ порога, порог в конфиге): имя, модуль, часы (из метаданных модуля), дата, уникальный verification-код.
- **6.2** Публичная страница проверки `/verify/[code]` — без auth: «Сертификат действителен: [имя], [модуль], [дата]» (имя показывать только при валидном коде; opt-out в настройках — тогда «Сертификат действителен» без имени).
- **6.3** Кнопки: скачать PDF, поделиться в LinkedIn (share-URL с OG-разметкой сертификата).
- **6.4** Профиль: раздел «Мои сертификаты»; enterprise-отчёт включает список сертификатов команды.
- **6.5** Генерация PDF — серверная (существующие python-инструменты), шаблон с логотипом; язык сертификата = язык пользователя.

**Приёмка:** завершение модуля с проходным баллом → сертификат скачивается; /verify/[code] подтверждает; невалидный код → «не найден»; opt-out скрывает имя.

## Фаза 7 — Голосовой режим AI-тьютора

**Цель:** hands-free обучение (дорога, спортзал). TTS уже есть — добавить вход голосом.

- **7.1** Web: кнопка микрофона в AI-тьюторе → Web Speech API (SpeechRecognition) где поддерживается; фолбэк — сообщение о неподдержке браузера. Распознанный текст показывается для подтверждения перед отправкой (медицинская точность: «преднизолон» vs «преднизон» — пользователь должен видеть, что распозналось).
- **7.2** Ответ — существующий TTS с автовоспроизведением в голосовом режиме; режим «разговор»: после ответа микрофон включается снова (переключаемо).
- **7.3** Mobile: expo-speech-recognition (или актуальный поддерживаемый пакет — проверить перед установкой) + существующий TTS.
- **7.4** Ограничение: голосовой ввод недоступен в patient-режиме для «красных флагов» — механика прежняя, guardrails серверные, фронт ничего не меняет в правилах.

**Приёмка:** полный голосовой цикл вопрос→ответ на Chrome desktop и в mobile-приложении; распознанный текст всегда виден до отправки.

